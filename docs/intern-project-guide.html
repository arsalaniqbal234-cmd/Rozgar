1. What problem are we solving?

People looking for remote work must search many job boards, compare inconsistent listings, and remember which roles they liked. Rozgar collects jobs from several sources into one searchable website. A visitor can filter jobs, read details, go to the employer to apply, and keep a private shortlist in their browser. An account holder can save a search so the system can later match new jobs to that interest.

The lead's program asks an intern to own the full outcome, from collection to website to deployment. Its longer-term target was a platform with at least 50 sources, autonomous data collection, and real user notifications. The current repository is a smaller but working beta. Present it that way.

Job boards → Python scrapers → PostgreSQL → FastAPI → Next.js website → job seeker
Optional side path: saved search → separate scheduler → Resend email, once configured

Words you should know

WordBeginner explanation
FrontendThe website the user sees and clicks.
Backend / APIThe server that receives requests, checks rules and identity, and reads or writes data. An API endpoint is a URL with a specific action.
ScraperCode that fetches a source's job data and converts it into a shared format.
DatabaseDurable storage. PostgreSQL holds jobs, saved searches, scrape runs, and alert-delivery records.
CacheA short-lived copy of a result. Redis can accelerate repeated API searches; the browser also briefly caches public results.
Scheduler / workerA separate running process that starts scraping and alert checks automatically. Deploying the API does not start it.
CI / migrationCI runs checks on code pushes. A database migration changes the stored schema in a controlled way.

3. How the system works

  1. A source adapter fetches jobs. BaseScraper spaces requests, retries temporary network/server errors, and validates a common NormalizedJob shape. Invalid individual jobs are skipped rather than throwing away a whole batch.
  2. The pipeline writes normalized jobs and keeps raw source information. It removes tracking parameters from application URLs and uses a URL fingerprint to prevent new copies with the same application link. Similar titles with different links may remain separate.
  3. FastAPI reads filtered jobs from PostgreSQL. The feed requests summary=true so large descriptions are not fetched for cards. The full description is requested for one job detail page.
  4. The browser sends search/filter parameters to /jobs. The API validates them, returns newest jobs first, and supports before_id cursor paging. The website shows loading, empty, and retry states.
  5. A shortlist is stored in that browser's localStorage. It needs no account, survives a reload on the same browser, and does not automatically sync to another phone or browser.
  6. For saved searches, Clerk signs the user in. The frontend passes a bearer token; the API verifies it and derives the user ID. The API obtains the user's verified primary email from Clerk. Each user can access only their own searches.
  7. If a separate scheduler and email credentials are running, new matching jobs become durable alert-delivery rows. A unique search/job pair and a stable provider idempotency key reduce duplicate messages. Email delivery is paused in the current public setup.
Design principle: PostgreSQL is the source of truth. Redis is an accelerator, not the only place where jobs live. The API is the authorization boundary; browser-supplied user IDs and email addresses cannot decide ownership.

5. How to test the public website, step by step

Start here. These tests need only your browser. Keep this PDF beside the website. Wait until job cards appear before typing; an automated test that filled the input before hydration did not retain the text.
Test 1 — The site and API are alive.
Open the website. You should see the Rozgar home page and job cards. In new tabs open API live and API ready. Expected: {"status":"ok"} for live and database:"ok" for ready. cache:"disabled" is the current production setting, not a broken database. □ Pass □ Fail
Test 2 — Search and filter real jobs.
Once cards appear, type Python in “Job title, skill, or company.” Expected: related results; the live request /jobs?keyword=Python... previously returned HTTP 200 with 9 results. Try Location, “Remote only,” “Salary listed only,” and a minimum salary. Results should narrow. A combination can reasonably show “No matching jobs yet.” Use “Clear filters” to reset. □ Pass □ Fail
Test 3 — Feed navigation and job details.
Try a “Python” quick-search button or a career path. If “Load more jobs” appears, click or scroll near the end and check that more cards arrive without replacing previous cards. Open a job title. Expected: detail page and an “Apply on employer” link leading to the original source; do not submit a real application just for the test. Some result sets have fewer than 20 jobs and therefore no extra page. □ Pass □ Fail
Test 4 — Shortlist.
Click the bookmark on one job card. Open “Shortlist,” reload that page, and confirm the saved job is still there. Remove it and confirm it disappears. Repeat in a private/incognito window: it will be a separate list, because the feature uses that browser's storage. □ Pass □ Fail
Test 5 — Interface controls.
Toggle dark mode and reload; the chosen theme should remain. Switch grid/list view. Resize the browser to a narrow phone width, and check that text and controls fit without horizontal scrolling. Press / while not typing in another field; search should receive focus. □ Pass □ Fail
Test 6 — Failure handling without changing production.
If the API temporarily fails, the feed should show an understandable message and “Try again.” The repository's Playwright tests simulate an HTTP 503 and verify this behavior; do not deliberately shut down the production database to test it. □ Automated test □ Not attempted

6. Test accounts and saved searches

Use your own test account. The current project has used Clerk development-instance settings, so do not treat this as a verified public launch. If Clerk rejects the domain, check the matching frontend/backend Clerk settings in Vercel before claiming the feature broken.

Test 7 — Sign in and create.
Click “Sign in.” Complete Clerk's flow with an address you control and verify it if prompted. Return to the job feed, type a keyword such as Python, then click “Save search.” Expected: a success message and an item under “Saved searches.” If you click without a keyword, the page should ask you to enter one. The saved-search page currently says email alerts are paused. □ Pass □ Fail
Test 8 — Ownership and deletion.
Reload “Saved searches”; the item should remain. Delete that test search; it should disappear. Sign out and open “Saved searches”: you should see a sign-in invitation, not the previous account's list. A different signed-in account should not see the first account's list. The backend's ownership test checks that another user also cannot delete it by ID. □ Pass □ Fail
Test 9 — Duplicate search.
Save the same keyword and same filters twice while signed in. The backend reuses the existing active record. Change a filter and save again; that is a different search. A user can keep at most 20 active searches. □ Pass □ Fail
Do not claim a received alert from these tests. Saving a search works independently of email. Public email delivery needs a verified sender, Resend key, backend Clerk secret, and a separate scheduler. WhatsApp delivery is not implemented.

7. Test the API without coding

Open FastAPI's interactive docs. A blue GET reads data; a POST starts or creates something; a DELETE removes/deactivates it. Expand an endpoint, select “Try it out,” enter parameters, then “Execute.”

Endpoint to inspectWhat to try and what you should see
GET /jobsUse keyword=Python, limit=5, summary=true. Expect HTTP 200 and a JSON list. For summary results, description is omitted. Try remote_only=true; a valid but empty list is possible.
GET /jobs/{job_id}Copy an ID from a result. Expect one job with an application URL. An invalid ID should return 404.
GET /health/live and /health/readyExpect 200. Ready checks the database; a 503 means that dependency failed.
GET /saved-searches/ or /health while signed outThese are protected. Without a valid bearer token, expect 401. Do not paste your login token into a shared screenshot or PDF.
POST /scrape/{source}Requires a private x-api-key and starts a real external fetch. Test it only in a local/test environment you control, with permission to call that source; do not treat it as a casual public button.

HTTP 200 means the request worked. HTTP 401 means unauthenticated; 403 means signed in but not allowed; 404 means item not found; 422 means invalid input; 503 means a required dependency is unavailable.

8. Test locally and run automated checks

Why test locally? It lets you inspect the backend, scheduler, Redis, and migrations without changing the live site. Start with automated checks if PostgreSQL/Redis are already available. Commands below use Windows PowerShell, as in the repository README.

  1. Open a terminal at the Rozgar repository root. Run git status. Do not edit or share Backend/.env; it contains private settings. Use .env.example to learn variable names.
  2. For a new environment, install Python 3.11, Node.js 24 and PostgreSQL. Redis is optional for normal reads but needed for the cache test. The example local database uses port 55432; edit your local environment only if your services use other ports.
  3. Open one terminal for the API and another for the website:
cd Backend
python -m venv venv                # Only if venv does not already exist

.\venv\Scripts\python.exe -m uvicorn app.main:app --reload

# In another terminal, from the Rozgar root:
cd Frontend
npm ci
npm run dev

Before starting, keep Backend/.env and Frontend/.env.local aligned: DATABASE_URL points to your PostgreSQL; NEXT_PUBLIC_API_URL=http://127.0.0.1:8000; local CORS/Clerk allowed origins include http://localhost:3000. Open local API docs and local website. If a port is already in use, stop the old process or choose a consistent new port.

11. Questions your lead may ask in an interview

Practice answering in your own words. The short answers below are examples to understand, not lines to memorize. If you cannot explain an answer, open the linked source file and trace the flow.

1. What is Rozgar's goal? Bring remote jobs from several boards into one searchable feed, let a visitor save roles, and prepare account-based notifications for new matches.
2. Is the roadmap complete? No. The live three-source beta and CI are real, but 10/50 source milestones, autonomous production scheduling, real email/WhatsApp delivery, and real-user metric evidence are not complete.
3. Why one GitHub repo but two Vercel projects? The apps share a product and release commit but use different runtimes. Vercel builds Frontend with Next.js and Backend with Python, retaining separate domains and environment settings.
4. What happens when a user types a keyword? React updates filters; the website sends a debounced /jobs request; FastAPI validates parameters; SQLAlchemy filters PostgreSQL jobs; the response renders cards.
5. What does summary=true improve? Feed cards omit large descriptions from both the SQL column fetch and returned JSON. The detail page fetches the full job when needed.
6. What is cursor paging? The next request passes the last displayed job ID as before_id and asks for older IDs, instead of repeatedly reading farther with a large offset.
7. How are duplicates detected? We normalize the application URL, remove common tracking parameters, hash it, and prevent new rows with the same fingerprint. We do not promise perfect semantic deduplication across different links.
8. Why keep raw source data? It helps investigate parsing mistakes and source changes without losing the original information behind a normalized job.
9. How does a scraper handle temporary failure? It spaces requests, retries network errors, 429, and server errors with increasing delay, and records a failed source run if the job pipeline cannot finish.
10. Why use PostgreSQL and Redis? PostgreSQL keeps durable truth. Redis can hold short-lived search responses. If Redis is absent or unavailable, the API bypasses it and reads PostgreSQL.
11. What does /health/live prove? What does ready prove? Live proves the API process responds. Ready also checks a database query and reports cache status. Neither proves that all scrapers or emails are healthy.
12. How do saved searches stay private? The API verifies Clerk's bearer token, derives the user ID itself, obtains the verified email from Clerk, and filters reads/deletes by owner. It does not trust a user ID typed by the browser.
13. Shortlist versus saved search? Shortlist is a browser-local list of individual jobs, available without sign-in. Saved search is a server-side, account-owned query with filters, intended for matching future jobs.
14. How do we avoid sending the same job alert twice? The database has one delivery record per search/job pair. Retry sends use a stable Resend idempotency key. Ambiguous old attempts move to review rather than blindly repeating.
15. Why is the scheduler a separate process? HTTP functions answer requests and may stop between them. Continuous periodic scraping/alert checks require a worker kept running separately; the Vercel API deployment alone is not that worker.
16. What is the measured performance improvement? In the recorded local 10,000-synthetic-job test, search p95 fell from 39.43 ms uncached to 11.89 ms cached, about 69.8% lower. Production Redis is currently disabled, so do not apply that claim to live users.
17. What do CI and browser tests cover? CI runs lint, types, backend tests, migration/benchmark checks, build and desktop/mobile browser tests. Browser tests use mocked jobs for repeatability; live source/provider tests remain separate.
18. What would you do when production fails? Find the failing layer with live/ready, API response and Vercel logs; preserve database state; repair and test, or promote the previous successful project deployment. Do not delete alert-delivery history to roll back code.
19. What would you improve next? Add approved sources toward 10 then 50, operate one scheduler, finish verified test email and Sentry gates, configure production Redis, and measure one week of real search latency and user activity.
20. What part did you personally build and verify? Be specific and truthful. Separate work you wrote or changed, work you reviewed, automated checks that passed, and external features you did not verify. A candid answer is stronger than claiming every subsystem is finished.
Follow-up preparation: Your lead may ask you to find an endpoint in Backend/app/routers, show the PostgreSQL model in Backend/app/models.py, explain a frontend state change in Frontend/app/page.tsx, or trace an alert from Backend/app/scheduler.py through Backend/app/alerts.py. Rehearse those four file paths.
